# 输出规格（硬规则）

报告要能被筛、被排期、被复测。文件名表达状态，正文表达证据。以下规则由 `assets/校验.ps1` 检查，改规则时两者要一起改。

## 1. 文件名

```text
<级别>-<功能类别>-<简要描述>-<状态>.md
```

| 片段 | 规则 |
| --- | --- |
| 级别 | `P0` / `P1` / `P2` / `P3`，必须与正文「问题级别」一致 |
| 功能类别 | 用例的一级模块；模块过宽时用「一级模块·二级模块」。没有用例时用功能域，例如「订单列表」「登录」 |
| 简要描述 | 8–20 个字符（中文即 8–20 个字），写现象；不写「测试不通过」「不符合预期」「bug」这类空话 |
| 状态 | 见下面的固定枚举；新发现问题默认 `待修复` |

硬性限制：

- 四段之间只用半角 `-`，段内不得再出现 `-`。
- 禁止字符：`\ / : * ? " < > |`、空格、换行、制表符；不能以点或空格结尾。
- 不使用 Windows 保留名：`CON`、`PRN`、`AUX`、`NUL`、`COM1`…`COM9`、`LPT1`…`LPT9`。
- 总长 ≤ 60 字符（含 `.md`）；同一输出目录内不得重名。
- 文件名里不写日期、轮次、经办人；这些放元信息或目录名。状态变化时直接重命名并同步 H1、元信息，不要用 `-修复版` 之类的副本。

状态枚举：

| 状态 | 含义 | 使用时机 |
| --- | --- | --- |
| `待修复` | 新发现，开发未处理 | 新输出默认值 |
| `修复中` | 开发处理中 | 开发认领后 |
| `待验证` | 开发已修复，等待复测 | 开发提交修复后 |
| `已验证` | 复测通过，待关闭或已确认 | 复测通过 |
| `已关闭` | 确认关闭 | 流程结束 |
| `不修复` | 确认不修复 | 产品 / 开发确认 |
| `延期` | 延期处理 | 排期外处理 |

正例：`P1-订单列表-切组后名单串组错误-待修复.md`、`P2-订单列表-长昵称挤压金额列-已验证.md`

反例：

| 错误文件名 | 原因 |
| --- | --- |
| `bug.md` | 缺级别、类别、描述、状态 |
| `P1-订单列表-测试不通过-待修复.md` | 描述空泛 |
| `P1-订单列表-金额列错位.md` | 缺状态 |
| `P1-订单列表-金额列错位-已修复待验证.md` | 状态不在枚举内 |
| `P1-订单列表-金额列错位-20261026-待修复.md` | 多余日期，段内还有 `-` |
| `P1-订单列表-金额/列错位-待修复.md` | 含非法字符 `/` |

## 2. 正文结构

固定顺序，二级标题不得改名、缺失或调换：

| 顺序 | 二级标题 | 必填 | 内容要求 |
| --- | --- | --- | --- |
| 1 | `## 问题级别` | 是 | `P0–P3` + 中文级别 + 1–3 句判定依据 |
| 2 | `## 文件目录` | 是 | 端 / 平台、页面或接口路径、源码位置、用例来源 |
| 3 | `## 问题描述` | 是 | 现象、复现步骤、复现条件与概率 |
| 4 | `## 预期结果` | 是 | 依据需求 / 用例 / 设计稿，逐点可验证 |
| 5 | `## 实际结果` | 是 | 实际现象；接口或日志的关键返回；与预期逐点对应 |
| 6 | `## 初步定位` | 是 | 责任方结论 + 可核查依据 + 建议下一步 + 已排除项（写法见第 7 节） |
| 7 | `## 问题截图` | 是 | 至少一张实际执行截图；无截图必须写原因 |
| 8 | `## 补充信息` | 否 | 接口原始响应、日志、录屏、关联问题、其他排查记录 |

- H1 与文件名（去掉 `.md`）完全一致，含状态。
- H1 前允许放一个元信息表；若放，必须含「当前状态」，且与文件名一致。
- 每个必填段落不得为空，不得残留占位符、`TBD`、`待补充`。

元信息表建议字段：

| 字段 | 示例 |
| --- | --- |
| 问题编号 | `BUG-20261026-001` |
| 发现轮次 | 首轮 / 次轮 / 主干 / 回归 |
| 发现时间 | `2026-10-26 18:40` |
| 执行端 / 环境 | Web / Chrome 129 / Windows 11，或 iOS 17.5 / iPhone 15 |
| 测试环境 / 账号 | `https://test.example.com` / 账号 `test_buyer_01`（密码不入报告） |
| 对应用例 | `ACT-SIGNUP-058`（用例优先级 `P1`）；无用例时写依据来源 |
| 复现概率 | 必现（3/3） / 偶现（2/5） |
| 当前状态 | 必须与文件名状态一致 |

## 3. 问题级别

| 级别 | 名称 | 判定标准 | 处理要求 |
| --- | --- | --- | --- |
| P0 | 阻塞 | 崩溃、白屏、无法进入；核心流程中断；权限越权或隐私泄露；数据错误或丢失；阻塞后续测试或发版 | 立即修复，修复前不发版 |
| P1 | 严重 | 核心功能结果错误或主流程受阻但有绕过；明显违反验收标准；影响多数用户或主要场景 | 本迭代必须修复 |
| P2 | 一般 | 边界值、兼容性、次要交互、视觉或文案偏差；不影响主流程 | 可排期修复 |
| P3 | 建议 | 体验优化、非验收项建议、样式微调 | 可选，不阻塞发版 |

定级注意事项：

- 级别按**实际影响**判定，不照抄用例优先级；用例优先级写进元信息。
- 同一根因导致多条用例失败：合并成一个文件，「对应用例」列全部编号。
- 同一用例在不同端表现或根因不同：拆成多个文件，用不同「简要描述」区分，不要用 `-小程序`、`-App` 这类后缀。
- 跨端同根因同表现：写一个文件，「文件目录」列两端路径，「实际结果」分别说明端差异。

## 4. 文件目录

按实际技术栈写，示例：

```text
- 端：Web / Chrome 129（或 iOS App / 微信小程序 / 服务端接口）
- 页面或接口：/order/list（或 pages/order/list、GET /api/orders）
- 源码文件：src/views/order/OrderList.vue:433
- 测试用例：testcase/2026-10-26-订单列表测试用例.csv / ORDER-058
```

要求：

- 源码用仓库相对路径，能定位到行号就带 `:行号`；定位不到就写清「端 + 页面或接口 + 用例编号」，并说明未定位原因，不要写「未知」。
- 跨端同一问题列多行。
- 用例文件写相对路径并带用例编号；没有用例时写清依据来源，例如「依据：用户口述验收标准 + 设计稿 Figma 链接」。

## 5. 截图

- 只放本次实际执行的截图，不得用设计稿、旧截图、网图顶替。
- 文件名：`<用例编号或问题编号>-<两位序号>-<简述>.png`；格式统一用 PNG。
- 放在 `<输出目录>/截图/`，Markdown 用相对路径：`![图1：说明](./截图/ORDER-058-01-金额列错位.png)`。
- 截图要包含关键区域和足够上下文；必要时用红框或箭头标注问题位置。
- 多图按 `01/02/03` 编号，每张图下面一行「图1：…」说明。
- 纯接口或数据问题，可附请求响应、日志截图或录屏链接。
- 无法截图时在「问题截图」写 `未截图说明：<具体原因>`，不能留空。

## 6. 依据来源

用户没有提供测试用例或需求文档时，报告仍然要能追溯：

- 「预期结果」写明依据（用户口述、设计稿、竞品对比、接口文档、历史行为），并标注哪个点是推测。
- 「对应用例」写 `无（依据：<来源>）`，但不要空着。
- 推测出的预期只能定 P2 及以下；影响核心流程的判断需要用户或产品确认后再定级。

## 7. 初步定位怎么写

每个问题都要给出责任方向，让开发拿到报告就知道该谁先看。结论只能从这个枚举里选：

| 结论 | 什么时候用 |
| --- | --- |
| `前端` | 接口返回的数据正确，页面渲染、交互、状态、校验、跳转、文案展示出错 |
| `后端` | 接口返回的字段、值、状态、错误码、排序或分页本身就错；或接口报错、超时、数据前后不一致 |
| `前后端都有` | 两边各有一处问题，例如前端按旧字段名取值、后端同时改了字段结构 |
| `需求或产品` | 需求自相矛盾、验收标准缺失、文案与设计稿冲突，技术上没有唯一正确实现 |
| `待确认` | 现有证据不足以区分两端，或没有源码 / 接口权限；必须写清缺什么证据 |

判断顺序（有证据就用证据，不要凭观感）：

1. 先看接口：抓 Network 响应、后端日志或接口文档，确认返回的字段、值、结构、状态码、排序与分页是否正确。
2. 再看前端：接口正确时查渲染与状态——模板 / 组件、数据转换、格式化、条件渲染、事件绑定、校验规则、路由参数。
3. 两边都看了仍对不上：标 `前后端都有`，把两处证据分别写出来。
4. 没有源码或抓不到接口：标 `待确认`，写出已排除的方向、还缺什么证据、该由谁提供。

判定依据必须可核查，至少包含一项：

- 接口证据：请求方法 + 路径 + 关键响应字段与值，如 `GET /api/orders → amount: 86.5`；
- 代码证据：仓库相对路径 + 行号，如 `src/views/order/OrderList.vue:433`；
- 运行证据：控制台报错原文、日志片段、录屏时间点。

写法要求：

- 「建议下一步」写清交给谁、先查哪个文件或字段，不要写「请开发排查」。
- 「排除项」写已排除的方向和理由；确实没排除任何项时写「无」，不要留空。
- 依据不足时宁可写 `待确认`，也不要为了显得专业硬归因；但 `待确认` 必须带上缺失证据的具体说明。
- 归因和定级是两件事：后端数据错误通常影响面更大，前端展示问题按实际影响定级，两者不要混为一谈。
