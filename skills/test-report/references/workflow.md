# 执行流程

格式规则见 `output-spec.md`。这里只讲怎么把一轮测试做完、做对。

## 1. 确认参数与范围

### 1.1 基础三问

| 参数 | 缺失时怎么办 |
| --- | --- |
| 测试用例位置（可选） | 用户说没有：按用户本次描述划定用例范围，自己编号（如 `ADHOC-001`）并写进元信息 |
| 需求 / 验收依据（可选） | 用户说没有：以用户口述、设计稿、接口文档、当前线上行为为预期，并在报告里注明依据 |
| 输出目录（必填） | 用户没给：给出建议目录（项目内 `test/<批次>`）再让用户确认，不要自己写到仓库根目录 |

### 1.2 按项目类型补问

先看仓库根目录判断类型（不用问），再补问对应项，能同轮问完就同轮：

| 类型 | 追加问 |
| --- | --- |
| Web / H5 | 有没有**测试环境地址**（URL）；有没有**测试账号**（账号 + 密码或登录方式、验证码怎么处理）；要不要连 VPN / 内网 |
| 微信小程序 | AppID、开发者工具是否已登录；测试账号 / 测试版权限 |
| Android / iOS App | 测试包（安装包或已装应用）、用哪台设备、测试账号 |
| 纯接口 / 后端 | base URL、鉴权方式（token / Cookie / 签名）、测试账号或密钥 |
| 桌面端 | 程序安装位置、测试账号 |

### 1.3 环境与账号的分寸

- 优先用测试 / 预发环境，不碰生产数据；不要注册新账号，不要猜账号。
- 报告与回复**不写明文密码**，只写账号标识（`test_buyer_01`）或「账号见群公告」；地址不要带 token 之类的敏感参数。
- 地址连不上、账号登不进：先确认要不要连 VPN、环境是否在维护；仍不行就退回只读验证或标未覆盖，并写进覆盖边界。
- 用户不愿给账号：问清替代方式（免登录环境、只读接口、已有登录态），按能测的范围做。
- 需要启动服务、装依赖、改配置、跑迁移时先问，不要擅自动手。

### 1.4 顺手确认

- 批次：首轮 / 次轮 / 主干 / 回归 / 自定义。输出目录已含批次就不重复。
- 执行端与环境：浏览器及版本、系统或机型、接口环境（测试 / 预发 / 线上）。
- 账号或测试数据是否可用；拿不到就先问，不要拿猜测填「复现条件」。

参数齐了再动手。已经答过的参数不要重复问；用户中途补充或改口径时以最新说法为准。

## 2. 开测前：能力与项目盘点

动手前先花几分钟把「能怎么测」摸清，比测到一半才发现没工具强。

### 2.1 项目类型（只读判断）

看仓库根目录和常见工程文件，判断这是哪类项目：

| 看到什么 | 大概率是 |
| --- | --- |
| `package.json` + `vite.config.*` / `webpack.config.*` / `next.config.*` / `nuxt.config.*` | Web 前端（含 SSR 框架） |
| `package.json` 依赖里有 `react` / `vue` / `svelte` / `angular` | 前端框架与版本，记进「文件目录」 |
| `project.config.json` + `app.json` / `app.wxss` / `*.wxml` | 微信小程序 |
| `app.json` + `uni-app` / `taro` 依赖 | 跨端（小程序 / H5 / App） |
| `pubspec.yaml` | Flutter |
| `build.gradle` / `Podfile` / `*.xcodeproj` + `react-native` 依赖 | 原生 App 或 RN |
| `pom.xml` / `build.gradle` / `go.mod` / `requirements.txt` / `*.csproj` | 后端服务 |

顺带记下：启动命令（`scripts` 段）、接口地址与代理配置（`.env*`、构建配置里的 proxy）、测试账号配置位置。**不要**为了看效果就装依赖、改配置、跑迁移；需要启动服务或改环境时先问用户。

### 2.2 能力盘点（逐项实测，别猜）

| 能力 | 怎么确认 | 不能用时怎么办 |
| --- | --- | --- |
| 读代码 | 直接读仓库文件、搜索关键实现 | 记「代码不可见」，定位只能写端 + 页面或接口 |
| 浏览器自动化 | 工具列表里有没有打开页面、取 DOM、截图的工具；先打开目标页，确认能拿到标题或 DOM | 改用接口 + 代码静态核对；界面类用例标未覆盖 |
| 真机（Android / iOS） | `adb devices`（Android）、`idevice_id -l` 或 Xcode 设备列表（iOS）；再确认能截到当前 App 画面 | 不声称测过真机，写「未连接设备」 |
| 小程序开发者工具 | 仓库有 `project.config.json` 时找开发者工具 CLI（`cli.bat` / `cli`），确认能否编译预览、截图 | 只能做代码与接口核对，界面标未覆盖 |
| 桌面应用自动化 | computer-use / 桌面自动化能力能否截图、点击、读控件树 | 记录不可用，改用可读到的线索 |
| 接口直连 | 有没有测试环境 base URL，能否发请求、看响应、抓包或读后端日志 | 以代码与页面现象推断，归因多写 `待确认` |

命令不存在、端口没开、服务连不上，一律记为「不可用」，不要编造结果，也不要用假截图充数。

### 2.3 选主路径

按可用能力选一两条主路径，其它作为补充：

- 有浏览器自动化、目标有界面：优先界面走查 + 截图，再用接口响应核对数据；
- 只有接口：走接口用例，能读后端代码就顺着字段找实现；
- 只有代码：静态核对渲染与校验逻辑，报告里注明「未实际执行」；
- 有真机或小程序工具：优先真实端，布局与兼容问题通常只在真机上出现。

### 2.4 覆盖边界

开测前先写下，最终回复要复述：

- 用的端与工具：例如「浏览器自动化 + 测试环境接口」；
- 计划覆盖范围：例如「订单列表页 12 条用例」；
- 已知覆盖缺口：例如「未连 iOS 真机，iOS 端只做代码核对」。

覆盖缺口直接影响报告可信度，漏报比漏测更糟。

## 3. 执行与留证

1. 按用例逐条执行，通过的打勾，失败或可疑的先记录：用例编号、端 / 环境、复现步骤、预期、实际。
2. 失败时立即截图（或录屏），并确认截图能看清问题位置；不要事后再补拍。
3. 失败时顺手抓归因证据：对应的请求与响应（Network / 抓包 / 后端日志）、控制台报错原文、可能相关的源码位置。归因没证据就只能写 `待确认`。
4. 偶现问题至少记录复现次数（如 2/5），能稳定复现的写必现。
5. 同一功能点可批量回归，但每条未通过用例的证据要能对上。

## 4. 定级、合并、拆分

- 先按 `output-spec.md` 的级别表定级，再决定文件名里的功能类别。
- 同一根因导致多条用例失败：合并为一个文件，元信息列出全部用例编号，不要一例一文件。
- 同一用例在不同端或不同根因下表现不同：拆成多个文件，用不同「简要描述」区分。
- 跨端同根因同表现：一个文件，文件目录列两端路径。
- 定级有争议时按较高的实际影响定，并在判定依据里写清理由。

## 5. 定位与归因

每个未通过项都要给责任方向，枚举与口径见 `output-spec.md` 第 7 节。执行时按这个顺序找证据：

1. **先看接口**：抓对应的请求与响应，确认字段名、值、结构、状态码、排序、分页是否与需求 / 设计一致。能读后端代码就顺着响应里的字段找到赋值逻辑，看是数据查询就错了，还是序列化 / 网关层丢了字段。
2. **再看前端**：接口正确时查渲染链路——组件模板、数据转换、格式化、条件渲染、事件绑定、表单校验、路由参数。能读前端代码就定位到具体文件与行号。
3. **两边都有问题**：分别写清两处证据，结论写 `前后端都有`，不要合并成一句模糊描述。
4. **证据不足**：结论写 `待确认`，写清已排除的方向、还缺什么证据、该由谁提供（例如「需要后端确认退款单金额口径」）。

补充约定：

- 不要写「看起来像前端」「可能是后端」这类没有证据的猜测；宁可 `待确认`。
- 归因影响交接：报告里「建议下一步」要能直接落到文件、接口或字段。
- 定位结论写在「初步定位」段，不要塞进「实际结果」段里混着说。
- 复测时如果定位结论变了，同步更新「初步定位」段。

## 6. 写文件

1. 复制 `assets/问题模板.md`，按命名规则重命名（含状态），放到输出目录。
2. 填写所有字段，删除全部占位符。模板里的复现步骤、复现条件要替换成真实内容。
3. 「初步定位」必须写成结论 + 可核查依据 + 建议下一步 + 排除项；没证据就写 `待确认` 并说明缺什么。
4. 元信息「当前状态」与文件名状态保持一致（新问题都是 `待修复`）。
5. 目录不存在时创建；不要把报告写进用例目录、需求目录或代码目录。

## 7. 截图归档

1. 截图放入 `<输出目录>/截图/`，命名 `<用例编号或问题编号>-<两位序号>-<简述>.png`。
2. 正文用相对路径引用 `./截图/…`，并确认链接能打开。
3. 无法截图（例如纯接口问题）时写 `未截图说明：<原因>`，不要留空，也不要拿别的图冒充。

## 8. 校验

在输出目录的上级或仓库根目录运行随包脚本：

```powershell
# 有 PowerShell 7
pwsh -NoProfile -File "<本技能目录>/assets/校验.ps1" -Path "<输出目录>"

# 只有 Windows PowerShell 5.1（默认执行策略会拦截脚本，必须加 Bypass）
powershell -NoProfile -ExecutionPolicy Bypass -File "<本技能目录>/assets/校验.ps1" -Path "<输出目录>"
```

- 通过：脚本退出码 0，输出每个文件的 `PASS` 与汇总行。
- 失败：按输出逐条修（文件名、状态、段落、截图路径、初步定位），修完重跑。
- 目录里没有待校验的 `.md` 时脚本返回 1，先确认是否真的没有任何失败项。
- 两个命令都不可用：按下面第 10 节清单人工核对，并在最终回复写明「未运行校验脚本」。

## 9. 复测与状态流转

- 复测通过：把状态改为 `已验证`，同时重命名文件、改 H1、改元信息「当前状态」；不要新建副本。
- 复测仍失败：保持 `待修复`，在原文件的「实际结果」或「补充信息」里追加本次复测结论与时间；定位变了就更新「初步定位」。
- 开发已修复但还没复测：状态写 `待验证`。
- 确认关闭、不修复、延期：在元信息与状态里对应修改，并在「补充信息」写清结论来源。

## 10. 完成前自检清单

- [ ] 每个失败用例都有对应文件，同根因已合并、多根因已拆分
- [ ] 文件名符合 `<级别>-<功能类别>-<简要描述>-<状态>.md`，级别与正文一致，长度 ≤ 60
- [ ] 状态在枚举内，与文件名、H1、元信息「当前状态」一致
- [ ] 七个必填二级标题齐全、顺序正确、无空段
- [ ] 「文件目录」含端 / 页面或接口 / 源码 / 用例（或依据来源）
- [ ] 「问题描述」含复现步骤与复现条件；「预期结果」「实际结果」逐点对应
- [ ] 「初步定位」有明确结论（或 `待确认` + 缺失证据说明），依据可核查，排除项已写
- [ ] 截图存在且相对链接可打开；无截图有原因
- [ ] 无 `{{占位符}}`、无 `TBD` / `待补充`、无「未知」
- [ ] 元信息写了测试环境 / 账号标识，且没有明文密码
- [ ] 已运行校验脚本并通过（或已说明未运行原因）
- [ ] 最终回复给出输出目录、按级别统计、按状态统计、定位分布、覆盖边界、未截图与未执行项

## 11. 最终回复

只报位置与统计，不粘贴全部问题正文；格式见 `SKILL.md` 第 7 节。
