# 测试验收

本技能是本模式的输出契约。测试结论可以有弹性，报告格式不行。格式细节以 `references/` 与 `assets/` 为准，不要凭记忆自己编。

## 1. 开工前

### 1.1 确认参数

先扫一眼仓库根目录判断项目类型（读文件即可，不用问用户），再把下面要问的一次问完（`ask_user_question` 支持多个问题，别拆成好几轮）。

基础三问，每轮都问：

1. **测试用例在哪里**（可选）：Excel / CSV / Markdown / 测试平台导出都行；没有就说没有。
2. **需求 / 验收依据在哪里**（可选）：需求说明、验收标准、设计稿、差异说明；没有就说没有。
3. **输出目录在哪里**（必填）：建议项目内 `test/<批次>`，截图写该目录下的 `截图/`。

按项目类型追加（看到哪类就问哪类，能和基础三问同轮问完就同轮）：

| 项目类型 | 追加问 |
| --- | --- |
| Web / H5 | **有没有测试环境地址**（URL）；**有没有测试账号**（账号 + 密码或登录方式、验证码怎么处理）；要不要连 VPN / 内网 |
| 微信小程序 | AppID、开发者工具里是否已登录；测试账号或测试版权限 |
| Android / iOS App | 测试包在哪（安装包或已装应用）、用哪台设备、测试账号 |
| 纯接口 / 后端 | 接口 base URL、鉴权方式（token / Cookie / 签名）、测试账号或密钥 |
| 桌面端 | 程序安装位置、测试账号 |

环境与账号的使用规则：

- 用户给了就用；没给先问，不要猜账号，不要注册新账号，不要用生产账号或真实用户数据。
- **报告和回复里不写明文密码**，只写账号标识（如 `test_buyer_01`）或「账号见群公告」；环境地址写可复现但不含敏感参数的地址。
- 地址连不上、账号登不进：先确认是否要连 VPN、环境是否在维护，再决定退回只读验证或标未覆盖，不要硬闯。
- 用户不愿提供账号时，问清替代方式（免登录测试环境、只读接口、已有登录态），按能测的范围做并写明限制。

### 1.2 盘点能力（先探测，再决定怎么测）

不要假设自己有什么工具，动手前逐项确认，能用就用，不能用就记下来：

- **代码看得到吗**：仓库是否可读；根目录是 `package.json`、`app.json` + `project.config.json`、`pubspec.yaml`、`build.gradle`、`Podfile`、`pom.xml`、`go.mod` 里的哪一种，据此判断项目类型与前端技术栈（Web / 小程序 / App / 混合 H5 / 服务端）。
- **能操控浏览器吗**：工具列表里有没有浏览器自动化能力（打开页面、取 DOM、截图）；有就先打开目标页，确认真的连得上再往下测。
- **电脑连了手机吗**：`adb devices`、iOS 设备列表之类能否列出真机；列不出来就不能声称测过真机。
- **是不是小程序**：仓库里有 `project.config.json` 才按小程序处理；再看微信开发者工具 CLI 是否可用、能否编译并预览。
- **有没有桌面自动化**：computer-use / 桌面自动化能不能截图、点击。
- **接口能直连吗**：有没有测试环境地址，能不能抓到响应、看到后端日志。
- **命令或工具不存在就记「不可用」**，不要假设它存在，更不要伪造截图、日志或响应。

把结论压成一句话（开测前用，最后写进最终回复）：
`本轮用 <工具 / 端> 测 <范围>；<某能力>不可用，所以 <某类用例> 只能静态核对或未覆盖`。
能力缺失不是停工理由，但覆盖边界必须说清，不能假装测过。

### 1.3 需要细节

- `references/output-spec.md`：格式硬规则、初步定位口径；
- `references/workflow.md`：执行、归因、复测、校验流程，其中第 2 节是能力与项目盘点的完整清单和判读表。

## 2. 输出单位

- 一条未通过用例 = 一个 Markdown 文件。
- 同一根因导致多条用例失败：合并成一个文件，元信息列出全部用例编号。
- 同一用例在不同端、不同根因或不同责任方向下表现不同：拆成多个文件，用不同「简要描述」区分。
- 已通过的用例不写文件；阻塞 / 未执行的用例也不当成问题，在最终回复里单列。
- 复测：通过就把原文件状态改成 `已验证`，同步改文件名、H1、元信息；仍失败保持 `待修复`，不要新建副本。

## 3. 硬性格式

- 文件名：`<级别>-<功能类别>-<简要描述>-<状态>.md`，四段只用半角 `-` 连接；简要描述 8–20 个字符；每段内部不得出现 `-`、空格和 `\ / : * ? " < > |`；总长 ≤ 60 字符；不能用 Windows 保留名。
- 级别：`P0` / `P1` / `P2` / `P3`，必须与正文「问题级别」一致。
- 状态：`待修复` / `修复中` / `待验证` / `已验证` / `已关闭` / `不修复` / `延期`；新发现问题默认 `待修复`。
- 正文七个二级标题按此顺序齐全且非空：`## 问题级别`、`## 文件目录`、`## 问题描述`、`## 预期结果`、`## 实际结果`、`## 初步定位`、`## 问题截图`；可选的 `## 补充信息` 放最后。
- H1 与文件名去掉 `.md` 后完全一致；放了元信息表就必须有「当前状态」，且与文件名状态一致。
- 禁止 `{{占位符}}`、`TBD`、`待补充`；填不出来的字段写清依据或原因，不要写「未知」。

## 4. 初步定位（必填）

每个失败项都要给出责任方向，让开发拿到报告就知道该谁先看：

- 结论只能是：`前端` / `后端` / `前后端都有` / `需求或产品` / `待确认`。
- 能看源码或接口响应时必须结合证据：接口请求 + 路径 + 关键字段值（如 `GET /api/orders → amount: 86.5`），或源码路径:行号（如 `src/views/order/OrderList.vue:433`），或控制台 / 日志原文。只写「看起来像前端」不算依据。
- 判断顺序：先看接口返回（字段、值、结构、状态码、排序、分页）是否正确；接口正确再看前端渲染与状态（模板、数据转换、格式化、条件渲染、事件绑定、校验、路由参数）。
- 看不到源码也抓不到接口时写 `待确认`，并写清缺什么证据、该找谁提供。
- 除结论外还要写「建议下一步」（交给谁、先查哪个文件或字段）和「排除项」（已排除什么、为什么）。

细节口径见 `references/output-spec.md` 第 7 节。

## 5. 截图

- 只用本次实际执行产生的截图，不用设计稿、旧图或网图。
- 存到 `<输出目录>/截图/`，命名 `<用例编号或问题编号>-<两位序号>-<简述>.png`。
- Markdown 用相对路径引用：`![图1：说明](./截图/编号-01-简述.png)`；多图按 `01/02/03` 编号并逐张说明。
- 确实无法截图时写 `未截图说明：<具体原因>`，不能留空。

## 6. 模板与校验

- 单条报告从 `assets/问题模板.md` 复制改写，删掉所有占位符。
- 写完运行随包校验脚本（有 PowerShell 7 用 `pwsh`，只有 Windows PowerShell 5.1 时用 `powershell` 并带 `-ExecutionPolicy Bypass`）：
  `pwsh -NoProfile -File "<本技能目录>/assets/校验.ps1" -Path "<输出目录>"`
  `powershell -NoProfile -ExecutionPolicy Bypass -File "<本技能目录>/assets/校验.ps1" -Path "<输出目录>"`
  把真实结果写进最终回复；校验不通过就改到通过为止。
- 两个都没有时按 `references/workflow.md` 末尾的自检清单人工核对，并在最终回复写明「未运行校验脚本」及原因。

## 7. 最终回复

只给位置与统计，不粘贴全部问题正文：

```text
问题汇总已输出到：<输出目录>
P0：n 条；P1：n 条；P2：n 条；P3：n 条
状态：待修复 n 条；待验证 n 条；已验证 n 条（按实际状态列）
定位：前端 n 条；后端 n 条；前后端 n 条；需求 n 条；待确认 n 条
覆盖：<端 / 工具>，用例 n 条；未覆盖：<哪些平台或场景>（原因）
未截图项：n 条（原因：...）
未执行 / 阻塞：n 条（原因：...）
校验结果：通过 / 未运行（原因）
```
